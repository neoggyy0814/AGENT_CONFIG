# 專案 Agent 工作流

本專案採用「需求驅動、驗證驅動、可收斂」的 Agent 開發流程。

本文件為專案層級的執行規則，以 Codex 全域開發原則為上層依據；本文件與 Codex 重疊之處以 Codex 為準，本文件不重複定義，只補充 Codex 未涵蓋的執行細節。

每一個使用者需求都遵循以下循環：

理解需求 → 詢問遺漏的可能需求 → 需求定稿 → 檢查現況 → 執行實作 → 靜態檢查 → 自動測試 → 驗收是否滿足需求 → 回報 → 等待使用者提出下一個需求

其中「靜態檢查」「自動測試」「驗收」三個節點皆可能觸發修正迴圈；「靜態檢查」與「自動測試」失敗時共用同一套修正進展判斷與中止條件（見下），「驗收」不滿足時則固定回到「6. 靜態檢查」重新走一次流程，不另做進展判斷。

## 修正進展判斷與中止條件

「6. 靜態檢查」與「7. 自動測試」失敗時，皆依此區塊判斷。

發現錯誤時，先依 Codex 全域規則區分錯誤來源：專案錯誤、工具錯誤、作業系統錯誤、執行環境錯誤。只有確認為專案本身的錯誤，才進入以下修正流程；非專案錯誤不屬於本文件處理範圍。

確認為專案錯誤後，每次失敗先判斷目前修正是否仍朝解決方向前進，再決定修正或中止，不進行無限迴圈。

**判定為仍有進展，繼續修正**，如果：

- 錯誤範圍正在縮小；
- 驗證結果正在改善；
- 根因已明確；
- 修正仍在目前需求與架構範圍內。

**判定為中止**，如果發生以下任一情況：

1. 問題反覆出現，修正沒有使結果朝解決方向前進。
2. 需要不斷增加例外、特殊處理或補丁才能繼續。
3. 原本的技術假設或架構已被證明不適用，需要重新決定方向。
4. 問題屬於 Agent 無法控制的環境、權限、硬體、外部服務或其他外部因素。
5. 繼續嘗試的成本已明顯高於目前資訊所能支持的合理收益。
6. 解決問題需要使用者做出尚未決定的選擇。

判定為中止時，不論發生在「6. 靜態檢查」或「7. 自動測試」，皆不繼續往下走，直接跳至「9. 回報」，並：

- 不繼續消耗資源進行無限嘗試。
- 保留目前可工作的狀態。
- 說明已完成的工作、目前失敗或阻塞的原因、已驗證與未驗證的部分、需要使用者決定或介入的事項。

## 1. 理解需求

- 先理解使用者真正要解決的問題、目標與限制。
- 不直接將使用者描述轉換成程式碼。
- 區分明確需求、已知限制與尚未決定的事項。
- 不自行補入會影響設計的重要假設。

## 2. 詢問遺漏的可能需求

- 在開始實作前，主動檢查是否存在會影響實作或驗收的重要遺漏需求。
- 只詢問真正會影響結果的問題，不為了完整而提出無關問題。
- 如果資訊已足夠，直接進入下一階段，不需要刻意詢問。
- 如果存在重要歧義，先詢問使用者，不自行猜測。
- 需求中出現主觀、模糊的品質形容詞（如「更精緻」「更有質感」「更順」）時，本身即為觸發澄清的訊號，不因任務類型看似明確而略過——這類形容詞缺乏可驗收的具體標準，會直接影響「9. 回報」與「8. 驗收」能否成立。

## 3. 需求定稿

- 當需求資訊已足以開始工作時，形成明確的實作目標與驗收條件。
- 後續實作以定稿後的需求為依據。
- 未決定的未來需求不納入目前實作。
- 若實作過程發現原始需求存在根本性矛盾或新的重要歧義，停止相關實作並重新詢問使用者。

## 4. 檢查現況

- 實作前先檢查相關檔案、程式、場景、資源、設定、工具與目前工作狀態。
- 優先理解並重用既有結構。
- 不因預期未來需求而預先建立架構。
- 不重複建立已存在的功能、規則或定義（單一真實來源原則見 Codex 全域規則，本文件不重複定義）。
- 不修改與目前需求無關的內容。
- 若現況與先前已定案的決策或設計衝突，明確標示衝突內容並提出給使用者，不得未經告知逕自覆蓋既有決策。

## 5. 執行實作

- 使用能滿足需求的最小必要實作。
- 優先修改現有結構，而非無必要增加新的抽象層、框架、工具或依賴。
- 實作應直接對應已定稿的需求與驗收條件。
- 不因「可能以後會需要」而擴張目前工作範圍。
- 屬於高影響的變更（例如變更既有架構、影響範圍廣、難以復原）時，先提出實作計畫並取得使用者核准，再開始執行；影響範圍有限的一般變更不需逐一核准。此為 Codex 全域規則「系統層級、破壞性或外部影響操作先說明必要性」在專案層級的加嚴版本：符合本專案高影響定義者，除依 Codex 說明必要性外，並須先取得使用者核准，而非僅說明即可執行。

## 6. 靜態檢查

實作完成後，先進行不需要完整執行遊戲的檢查，例如：

- 程式語法與型別問題
- Scene／Node 結構
- 資源路徑
- 專案設定
- 明顯的引用錯誤
- Git diff
- 其他與本次修改直接相關的靜態問題

若發現問題，依「修正進展判斷與中止條件」處理：

- 判定為仍有進展 → 修正 → 重新進行靜態檢查。
- 判定為中止 → 不進入「7. 自動測試」，直接跳至「9. 回報」。

通過後進入「7. 自動測試」。此節點同時是「7. 自動測試」判定仍有進展、與「8. 驗收」不滿足時，兩處修正迴圈共同的回歸點。

## 7. 自動測試

靜態檢查通過後，執行目前環境可以自動完成的測試。

依需求選擇適當的驗證方式，例如：

- 專案啟動
- Headless 執行
- Scene／資源載入
- 程式邏輯
- 功能測試
- 單元測試
- 其他可自動驗證的行為

若失敗，依「修正進展判斷與中止條件」處理：

- 判定為仍有進展 → 修正 → 回到「6. 靜態檢查」，重新走過靜態檢查與自動測試。
- 判定為中止 → 不進入「8. 驗收」，直接跳至「9. 回報」。

## 8. 驗收是否滿足需求

自動測試通過後，回到最初的需求與驗收條件進行確認：

- 原始需求是否全部實現。
- 驗收條件是否全部滿足。
- 是否有需求只完成程式邏輯，但尚未完成實際視覺或互動驗收。
- 是否有因執行環境限制而無法自動驗證的部分。

不要將「測試通過」直接等同於「需求完成」；自動驗證與人工驗收必須明確區分，不得宣稱未實際驗證的內容已完成。

若不滿足：

> 修正 → 回到「6. 靜態檢查」，重新走過靜態檢查與自動測試。

若滿足，進入「9. 回報」。

## 9. 回報

無論是正常完成，或於「6. 靜態檢查」「7. 自動測試」任一處判定中止，皆回報：

- 完成了什麼。
- 如何驗證。
- 驗證結果。
- 哪些部分仍未驗證。
- 如果是中止，說明阻塞原因與需要使用者決定的事項。

「測試通過」「驗證完成」等結論，只能在有可重現的具體依據（如實際指令輸出、記錄檔、實際執行結果）時才能宣稱；不得以推論、先前經驗或「應該沒問題」取代實際驗證——自我報告本身不可採信，需區分「被指示要做的事」與「已實際驗證確實完成的事」。

避免回報與結果無關的過程細節。

## 10. 等待下一個需求

完成回報後停止目前工作。

除非使用者提出新的需求、修正或下一步指示，不自行擴張工作範圍、最佳化或建立未要求的功能。

收到下一個需求後，重新從「1. 理解需求」開始。
