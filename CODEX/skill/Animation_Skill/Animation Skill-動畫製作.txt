# 2D 角色／物件動畫資產 Skill

## 目的

這份 Skill 是一個生成器（generator），不是逐動作各寫一套的規則集：只要需求涉及 2D 角色或物件產生連續視覺動作——行走、跑步、待機、攻擊、施法、受傷、死亡、跳躍、互動，或任何其他多影格動作——都必須走完下面完整的動畫資產流程。新增動作不需要新增規則，全部進入同一條流程。

目標流程：

動畫需求 → 動畫規格 → 來源圖片生成 → 影格切割 → 影格對齊 → 動畫資源建立 → 遊戲整合 → 視覺驗證

單一靜態圖片透過移動、位移、旋轉、縮放或水平翻轉，永遠不能替代真正需要的影格式動畫。

## 這份 Skill 存在的原因

以下是根因層級的失敗模式，不是背景故事——每次都要明確檢查：

- **移動需求經常暗中夾帶動畫需求。**「角色可以移動」「依方向翻轉」「可以在移動途中改變目標」「抵達後停止」是行為／邏輯需求。「有行走動畫」是同一段話裡另一個獨立的視覺需求。即使使用者把它們寫在同一段裡，也要當成兩個需求處理——不能讓比較容易做到的那個（移動）頂替比較難的那個（動畫）。
- **完成移動不等於完成動畫。** 對一張靜態圖片做位置改變、水平翻轉、縮放或旋轉，同時可以是「移動實作完全做到」跟「動畫需求完全沒做到」——這兩者不是同一件事的不同程度，必須分開驗證。
- **AI 生成的圖片是素材，不是可直接上線的資產**，即使它就是為了回應「做一個行走動畫」而生成的。沒有這套流程把關，預設的失敗模式是：生成一張圖 → 接到 AnimatedSprite2D → 重複播放同一張影格，或用 Transform 模擬動作。這種結果絕對不能回報成「動畫已完成」。
- **`flip_h`（或任何水平鏡像）只能鏡像既有視角，不能替代缺少的視角。** 正面行走循環左右翻轉後仍然是正面，不會變成側面或背面。如果需求要求角色能明顯轉身（例如背對或面向鏡頭，而不只是左右鏡像），單靠鏡像無法滿足——見第9節。
- **生成物的自我檢查，預設就是橡皮圖章，不是真正的檢查。** 最常見的失敗模式不是「反覆生成一直失敗、沒人發現」，而是在沒有依照這個動作真正的判準逐項檢查的情況下，就宣稱結果合格。除非檢查產出的是逐項判準、附帶視覺依據的明確判斷，否則檢查結果本身不可信——見第5節。
- **文字描述無法可靠地表達結構性的動作正確性**（肢體交替、時序、移動部位之間的空間關係），這點對任何動作都成立，不只是行走。當真實檢查發現反覆生成始終無法在這方面收斂時，解法不是寫更詳細的文字描述，也不是無限重新生成——見第5節的參考圖升級機制。

## 與其他專案規則的關係

- 這份 Skill 是 Codex 全域規則與 `agent-workflow.md` 在專案層級的補充，不重新定義靜態檢查行為、核准門檻，或修正/中止邏輯。
- 當影格生成或切割反覆無法產出可用結果時，依 `agent-workflow.md` 的**修正進展判斷與中止條件**停止——不要無限重新生成素材，這裡也不另外定義一套停止規則。
- 這份 Skill 適用於 `agent-workflow.md`「4. 檢查現況」與「5. 執行實作」這兩步，只要需求涉及角色或物件需要連續視覺動作。
- 本文件只定義內容規則。是否能被特定 Codex/Agent 環境實際載入，取決於該環境自己的 Skill 檔案格式／驗證規範，這是另一個層級的問題——整合時請以該環境自己的驗證工具為準。

## 1. 判斷是否需要動畫

在實作角色移動或互動之前，檢查需求——包括主要用移動或邏輯描述的需求——是否隱含任何連續視覺動作。

如果描述隱含隨時間產生視覺變化，就當作動畫需求。觸發用詞不限於移動類，也包括任何動作專屬的動畫描述，例如：「行走／行走動畫」「跑步」「攻擊動畫」「施法／法術動畫」「受擊反應」「死亡動畫」「待機動畫」「表情動作」「表情變化」「移動時播放動畫」「[任何動作]時使用不同影格」。這份清單只是舉例，不是全部——同一個測試（描述是否隱含隨時間的視覺變化）要套用在任何動作上，不只是移動類。

移動相關的行為需求——改變方向、移動途中改變目標、抵達後停止——本身不會構成動畫需求，這些描述的是移動邏輯，不是視覺變化。只有在動畫需求已經因為其他原因成立時，這些行為才需要被反映到動畫狀態上（見第10節）。

不得將這類需求解讀為只需要：

- 移動靜態圖片
- 改變圖片位置
- 水平翻轉圖片
- 套用 Transform（縮放／旋轉）
- 改變單一圖片屬性

如果需要連續動作，就必須建立或取得多個動畫影格——不論需求其餘部分（移動邏輯、鎖定目標、狀態轉換）怎麼實作，這點都不能妥協。

## 2. 建立動畫前先定義規格

在產生或處理動畫圖片之前，先決定目前任務實際需要的最小動畫規格。至少要定義：

- 動作名稱
- 影格數量
- 影格順序
- 播放速度
- 是否循環
- 影格尺寸
- 角色錨點／對齊基準
- 需要的視角數量，以及哪些視角可以透過水平翻轉互相取代（見第9節）——不預設任何預設值，必須從需求本身判斷
- 整合模式：連續狀態驅動，或事件觸發的一次性動畫（見第10節）——如果是觸發型，還要定義能否被打斷，以及播放完畢後回到哪個狀態
- 這個動作專屬的正確性判準——什麼樣的視覺結果算對、什麼算錯（例如：移動循環看肢體交替；打擊動作看預備／命中／收招；施法看蓄力／釋放）。每個動作各自定義，不存在放諸四海皆準的模板，也不能假設某個動作的判準可以直接套用到另一個動作上。

不要自行增加不必要的動畫需求。簡單的行走動畫只需要少量視覺上有明顯差異的影格即可，除非使用者明確要求更細緻的動畫。

## 3. 產生動畫來源圖片

產生一組視覺上連續的姿勢，而不是單張靜態角色圖片。可行時優先使用包含多個影格的單一 sprite sheet 作為來源圖片。

每個影格應：

- 描繪同一個角色，保持相同的設計、視覺風格、比例、視角、身材比例、光線與色調
- 依第2節定義的這個動作的正確性判準，呈現有意義的進展——不只是影格之間看起來不一樣而已
- 佔用一致的影格區域與地面／錨點位置

不要假設單一通用姿勢模板適用於所有動作類型。移動、打擊、施法、表情動作各自有自己的正確性判準（定義於第2節）與自己的關鍵姿勢結構——不要把某個動作的姿勢分解方式，預設套用到另一個動作上。

如果這個動作已經有可用的參考圖——不論是使用者提供，或是同一角色其他已通過檢查的視角／動作先前生成的結果——直接把它當作生成輸入使用，不要預設一定要先跑純文字生成。使用參考圖作為生成輸入時，只萃取動作／姿勢特徵——肢體交替、接觸／passing 時序、次要元素動態，以及其他跟這個動作的正確性判準（第2節）相關的結構特徵。不得沿用參考圖的角色設計、服裝、畫風、色調，或任何浮水印／背景痕跡。專案本身既有的角色設計優先，參考圖只管動作。

在生成之前，逐格個別指定姿勢——腿部／肢體位置、身體高度、次要元素動態（披風、頭髮、寬鬆衣物），依這個動作的正確性判準決定——而不是對整張圖只下一個籠統指令（例如「生成一個行走動畫」），期待生成方式自己推論出正確結構。如果生成方式或工具無法接受逐格姿勢指令，就一次生成並檢查一格，而不是整張圖一次處理。

> **範例（僅供參考，不得原封不動套用到其他動作）。** 移動循環的正確性判準通常包括：前導肢體在循環中交替（一個行走循環至少要有一個左腳在前、一個右腳在前的接觸姿勢）；接觸姿勢與 passing 姿勢之間有一定的垂直起伏；手臂反向擺動；披風／斗篷／頭髮等次要元素會隨步伐反應。經典的4姿勢分解：(1) Contact-A——前腳踩地、後腳拖曳、身體最低；(2) Passing-1——雙腳在身體下方交叉、身體最高；(3) Contact-B——鏡射姿勢1、左右腳互換；(4) Passing-2——鏡射姿勢2。其他動作需要依自己的正確性判準,建立自己的分解方式——例如打擊動作可能用預備／命中／收招，而不是肢體交替。

把來源圖片當作動畫素材，不是最終可上線的資產。

## 4. 優先使用規則化的 Sprite Sheet 排列

產生多個影格時，優先使用可預測的網格或明確結構化的排列——一列代表一個動畫、一格代表一個影格、所有格子尺寸相同。

如果之後需要自動切割，要避免不規則排列。如果生成方式無法可靠產生乾淨、規則的 sprite sheet，不要默默假設結果已經可以用於動畫——匯入遊戲前先檢查。

## 5. 檢查生成的圖片

由剛完成生成的同一個流程自己做檢查，預設是不可靠的。這種自我檢查通常會以兩種方式失敗：沒有真正檢查（從「有N張影格存在」直接跳到「繼續進行」），或是表面上確認（把「影格看起來彼此不同」當成正確性的證據，卻沒有真的對照判準檢查）。這兩者都是自我報告的失敗——執行了檢查這個動作，不代表檢查本身可靠——必須用跟任何其他未經驗證的完成宣稱同樣的懷疑態度對待（見第11節／`agent-workflow.md` 的自我報告規則）。

要讓檢查是真的檢查、而不是橡皮圖章：

- 對照第2節定義的每一項正確性判準逐一評估，針對每一項給出明確判斷——符合或不符合，並附上支持這個判斷的具體視覺依據——而不是給一個整體印象。
- 如果有視覺／多模態檢視能力可用，就實際用它逐項對照圖片檢查；生成端的中繼資料（例如「產生了4張影格」）不能作為動作本身正確的證據。
- 也要檢查比較基本、跟動作本身無關的屬性：可辨識的影格數量、影格邊界、圖片尺寸、透明背景／背景狀態、角色一致性、角色比例（若存在多個視角，須包含跨視角的一致性）、腳部／地面位置、身體位置、朝向、是否意外裁切、是否有重複或缺少影格、是否有不需要的瑕疵。

如果生成的圖片無法提供可用的動畫影格，不要透過把靜態圖片當成動畫來繞過問題。適當時重新生成或修改來源圖片。

如果真實檢查——不是橡皮圖章式的檢查——發現反覆重新生成始終無法朝定義好的正確性判準收斂，先套用 `agent-workflow.md` 的修正進展判斷：每次嘗試是不是真的更接近目標，還是同樣的結構性缺口不斷重複、跟提示詞怎麼修改無關？當反覆出現的缺口是文字提示反覆修改都無法解決的結構性動作特性——肢體交替、時序、移動部位之間的空間關係——這對應到 `agent-workflow.md` 中止判準裡「解決問題需要使用者做出尚未決定的選擇」這一項：停止繼續在純文字提示上打轉，改為請使用者提供想要的動作的參考圖或示範圖，而不是無限重新生成。如果此時已經有可用的參考圖，直接使用它，不需要另外再要求提供、也不必再繼續純文字嘗試。

## 6. 切割個別影格

除非執行系統已明確設定為以 sprite sheet 方式解讀，否則不要直接把完整的生成圖片當成角色貼圖使用。

依照來源圖片的實際排列方式，切割或設定個別影格區域。每個影格必須具有相同寬度、相同高度、一致的座標系統、正確的順序。優先依已知的影格尺寸或網格座標進行決定性的切割；如果來源具有共同的影格結構，不要為每個影格任意使用不同的裁切尺寸。

## 7. 對齊動畫影格

影格對齊是必要步驟，不是可有可無的修飾。在完成前，確認角色不會因為裁切方式不一致，而在影格之間出現跳動、漂移或比例變化。

依照素材類型使用一致的錨點——例如：移動類動作（走、跑、待機）用角色的腳部／地面接觸點；戰鬥或施法類動作用武器、判定框或特效原點；表情氣泡、單獨換臉這類非全身的疊加素材，則用相對於角色或畫面的固定偏移。不論套用哪種錨點，都要在影格之間保持穩定——角色比例、選定的錨點位置、影格尺寸、視覺上的攝影機位置都不應該漂移——除非動畫本身刻意改變它們。角色內部的姿勢可以改變，但影格相對於錨點的座標系統不可以改變。

如果不同姿勢周圍的透明空間數量不同，應該透過一致的影格對齊來修正，而不是讓角色在播放時產生視覺位移。

## 8. 建立遊戲中的動畫

完成切割與對齊後，建立實際的動畫資源。在 Godot 中，優先使用專案既有的動畫系統（AnimatedSprite2D、SpriteFrames、AnimationPlayer）。除非目前專案確實需要，否則不要額外引入新的動畫框架。

設定：動畫名稱、影格順序、影格播放時間／FPS、循環方式、預設動畫、播放狀態。遊戲中的動畫應該參照已處理完成的影格，而不是直接依賴原始生成來源。

## 9. 處理視角與方向

這裡經常被混為一談的兩件事，必須分開：

- **視角（Viewpoint）**：圖片實際描繪的是角色的哪一側（例如正面／向下、背面／向上、側面）。不同的視角需要不同的來源圖片，不能透過翻轉、縮放或任何其他變換，從另一個視角推導出來。
- **鏡像（Mirroring）**：把某一個視角的圖片重複用於它的水平鏡像方向（例如面向右的側面圖，翻轉後面向左）。`flip_h` 只能做鏡像，不能替代缺少的視角。正面影格組水平翻轉後仍然是正面，永遠不會變成側面或背面。

在產生方向相關的圖片之前，先從需求判斷實際需要幾個不同的視角——不要預設一個預設值。例如：

- 只有單一視角（例如固定角度的圖示，或角色從不明顯轉身）：1個視角，不需要鏡像
- 經典3視角組（正面／向下、背面／向上、側面）：側面透過鏡像涵蓋左右兩側；正面跟背面彼此不互為鏡像，必須各自生成
- 4方向或8方向移動（例如俯視或等角遊戲）：依方向配置實際需要的視角各自生成；只鏡像真正互為水平鏡像的那幾對（例如「左下」與「右下」通常互為鏡像；「上」／「下」不互為任何鏡像）

如果需求裡有幾個視角並不清楚——例如需求只寫「依方向翻轉」，沒有說明角色是否需要明顯轉身以背對或面向鏡頭——依第1節／`agent-workflow.md` 的歧義規則，當作缺漏需求處理，先問使用者，不要預設用單一視角加翻轉解決，也不要預設要做完整的多視角組。

決定好需要的視角之後，在每個視角內部，優先用水平翻轉取代重複生成鏡像方向的圖片。只有在視覺設計本身不是左右對稱，或使用者明確要求時，才需要另外生成鏡像素材。視角／方向處理不得破壞影格對齊或播放。

當角色或物件有多個必要視角時，渲染比例與錨點位置必須跨視角保持一致，不是只有各視角內部自己對齊就好。切換視角動畫時，角色的可視高度或錨點偏移發生變化，即使每個視角各自都通過第7節的內部對齊檢查，仍然視為不合格。這必須明確獨立檢查——單一視角內部一致，不代表跨視角也一致。

## 10. 將動畫與角色狀態整合

動畫必須對應角色實際的狀態。這裡存在兩種不同的模式——在第2節定義規格時就要判斷這個動作屬於哪一種，因為兩者需要不同的整合邏輯。

**連續、狀態驅動的動畫**（待機、走、跑——追蹤某個持續狀態的動畫）：

- 狀態開始 → 開始播放對應動畫
- 狀態持續 → 持續播放動畫
- 狀態結束 → 停止動畫或回到待機
- 相關的子條件改變（例如朝向、移動目標）→ 相應更新，但不破壞動畫播放
- 狀態完全解除 → 回到適當的非活躍狀態

**觸發型、事件驅動的一次性動畫**（攻擊、施法、受擊反應、死亡、表情變化——由離散事件觸發，而非持續狀態）：

- 事件觸發動畫 → 播放一次（或依第2節定義的循環規格），不持續播放
- 定義動畫能否被打斷（例如被移動、其他動作或受擊打斷），以及打斷後的處理方式
- 播放完成後，依這個動作對角色而言是**終結性**還是**非終結性**，定義接下來要做什麼：
  - 非終結性（攻擊、施法、受擊反應、表情變化）→ 明確回到正確的先前／預設狀態（例如攻擊動畫播完要回到待機，而不是停在最後一格）
  - 終結性（死亡，或任何會結束該實體活躍狀態的動作）→ 不回到任何先前／預設狀態，而是停在最後一格、移除／despawn，或依需求規定的方式轉換到結束流程
  - 不論哪一種，都必須經過驗證，不能只是假設
- 如果兩個觸發型動畫（或一個觸發型跟一個連續型）可能重疊，要定義誰優先，讓動畫狀態不會同時存在兩個互相矛盾的權威來源

不論哪一種模式，移動／邏輯程式碼跟動畫狀態都不能變成兩個各自獨立、可能互相矛盾的權威來源——動畫狀態應該反映實際的遊戲狀態。

## 11. 視覺驗證動畫

自動檢查本身不足以驗證動畫的視覺品質。

自動驗證可以確認：必要資源是否存在、預期影格數是否存在、影格尺寸是否有效、資源是否可以載入、動畫名稱是否正確、場景是否可以載入、腳本是否參照有效資源，以及專案是否可以在沒有相關錯誤的情況下執行。

以下項目需要人工視覺驗證：影格之間的連續性、對齊是否正確、是否出現腳部滑動、角色是否抖動、是否出現非預期的比例變化、方向翻轉是否正確、影格順序是否正確、開始／停止時機是否正確，以及生成圖片本身的視覺品質。

依 `agent-workflow.md` 的回報規則——自我宣稱的完成，若沒有可重現的依據就不可信：如果目前的執行環境無法實際顯示並檢查動畫，不得宣稱視覺驗證已經完成。

## 12. 完成條件

動畫任務只有在以下所有適用階段都完成時，才算完成：

1. 已確認需要的動作。
2. 已定義動畫規格。
3. 如果需要連續動畫，已建立多個動作影格。
4. 已對照第2節的正確性判準，對來源圖片進行真實檢查——逐項判準給出判斷，而不是橡皮圖章式通過。
5. 已切割影格或正確設定影格區域。
6. 已完成影格對齊。
7. 已建立遊戲中的動畫資源。
8. 在適用的情況下，已生成所需的視角，並依規格實作鏡像／方向處理。
9. 已將動畫狀態與相關遊戲狀態連接。
10. 已在可行範圍內完成自動驗證。
11. 在需要時已完成人工視覺驗收。

單純生成一張角色圖片，不符合上述完成條件。

## 13. 避免常見的捷徑

以下方式都不算完成一個必要的動畫需求：

- 讓靜態圖片在畫面上移動
- 翻轉靜態圖片
- 重複播放同一個影格
- 透過縮放或旋轉模擬動作
- 只生成一張角色圖片，假設之後可以再製作動畫
- 未經驗證就直接使用 AI 生成的 sprite sheet
- 讓每個影格具有不相關的比例或位置
- 因為專案可以正常啟動，就宣稱動畫已完成

如果需求要求連續動作，必須產出完整的素材與遊戲整合流程——而不是它的替代品。

## 14. 範圍與停止條件

只建立目前任務實際需要的動畫素材。不要預先生成未使用的角色動作、不需要的方向、未使用的動畫狀態、大型動畫素材庫，或未來的角色變體。

當真實檢查（第5節）發現某個特定視角、動作或影格組存在結構性缺口時，修正範圍限定在該缺口本身。已通過真實檢查的視角、動作或影格組不需要重新生成或重新驗證，除非這次修正可能影響到它們（例如共用的角色基礎設計有變動）。

如果生成的圖片反覆無法提供可用的影格，依 `agent-workflow.md` 的修正進展判斷與中止條件停止。優先取得清楚、最小、可運作的動畫，而不是不斷增加複雜度的素材生成流程。

## 預期工作流程

典型的 2D 角色行走動畫：

需求 → 定義行走循環 → 生成多影格來源圖片 → 檢查來源圖片 → 切割影格 → 對齊影格 → 建立 SpriteFrames／動畫 → 將動畫連接至移動狀態 → 設定水平方向翻轉 → 執行自動檢查 → 人工檢查動畫 → 回報完成與驗證狀態
